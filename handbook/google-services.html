2. The Apps Scripts

The pages call 25 Apps Script web apps. Each has an address of the form script.google.com/macros/s/AKfycb…/exec; the table identifies them by the first characters after AKfycb, which you can search for in the page code. The full project list can be seen at script.google.com → My Projects (check both Google accounts). Scripts attached to a Sheet are opened from that Sheet’s Extensions → Apps Script menu.

Retiring an old project safelyRather than deleting, first open it, check Triggers (clock icon) and remove any, then Deploy → Manage deployments → Archive. Leave it a month; if nothing has broken, it can be moved to the bin. Keep a text copy of its code in Drive.

Keys inside scripts

Our Story, Fireside Talks, Resident Submissions, the Asset Register and Facility Calendar Sync check a key or PIN before handing out private data or accepting changes, and Event Media and Travel Pics check name and unit privately. That is the right design, but for all except the Asset Register (and the gallery unit checks) the same key is also written in a public page, so it offers the same “curtain” protection as the PINs. Keys are recorded in the Hub Secrets Register, never here.

3. Changing a script safely

  1. Open the project (from My Projects, or the Sheet’s Extensions → Apps Script). Before editing, copy the whole code into a text file as a backup.
  2. Make the change and click the save icon.
  3. Publish it without changing the address: Deploy → Manage deployments → pencil icon on the existing web app → Version: New version → Deploy. The /exec address stays the same, so no page needs changing.
Avoid “New deployment”Deploy → New deployment creates a brand-new address. Every page that uses the old address would then have to be edited. Only do this deliberately, and search the repo for the old ID first.

For residents to use a page without signing in to Google, its web app must be deployed with Execute as: Me (the owner) and Who has access: Anyone (to confirm for each script). That is what allows residents to use the pages without signing in to Google — and also why a script should check a key or PIN itself before handing out private data.

Some scripts also run on a timer or event (“trigger”). Triggers are listed under the clock icon in the Apps Script editor (or My Triggers on the projects page) and run as the account that created them. Known triggers:

  • Event Registration Reminder Script — daily checkUpcomingEvents (reminder emails 7 days before an event) and updateSummary when the registration form is submitted.
  • Web Content Manager — daily at 8 am, checkExpiringAnnouncements.
  • Finances — processNewCorrections every 15 minutes; checkAndGenerateReport daily at 6 am (makes the report on the third Sunday).
  • Facility Calendar Sync — a monthly run of autoGenerateRecurringMonths (to confirm), and short-lived “resume” timers that a full sync creates and removes itself.

5. Drive folders, Calendar and other Google pieces

  • Meeting and document folders (Upload a Document): Annual General Meetings, RC Monthly Meetings, Residents Quarterly Meetings, SC Monthly Meetings, Newsletters, Community Contributions, Monthly Financial Reports, Bank Statements, Aveo Documents. The Residents Only page groups financial documents into quarterly sub-folders automatically.
  • Event Photos & Videos — one sub-folder per event; Travel Pics — one sub-folder per album. Each script is locked to its own folder.
  • Documents shown on the Hub open through view-document.html?id=…, which displays a Drive file inside the Hub. The file must be shared “Anyone with the link can view”.
  • Google Calendar of rabd.ctee@gmail.com is embedded on the Calendar page; it is filled automatically from the Master Schedule Sheet.
  • Google Sheets API key (written in index.html) lets the Home page read the Web Content Manager Sheet. It should be restricted, in Google Cloud Console, to the Sheets API and to bdrv.au.
