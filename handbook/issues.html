Issues, Actions & Concerns

1. The Issues Tracker

In one sentenceEvery village issue raised with Village Management is one row in the progress-tracker-data Sheet; the Community Manager, Manor Advisor and RC each add their notes through their own page, and residents see progress on the public “What We’re Working On” page.

The Sheet

progress-tracker-data (owned by the personal account — see ownership risk). Columns: A issue number (ISS-01, ISS-02… assigned automatically), B category, C topic, D notes, E status (new issues start “Not Started”), F source, G last updated (Brisbane time, set by the script). The tab is published as a CSV feed and read by all the issue pages.

Two scripts update the same Sheet

The Issues Tracker script (committee account) and the Progress Tracker Email Notification script (personal account) both add and update rows. The second also emails rabd.ctee each time and writes a ✅/⚠️/❌ message in cell J1 of the Sheet describing its last save — the first place to look if an update didn’t stick. Which page uses which script is still to be confirmed (probably the Manor Advisor’s page uses the second).

Issue numbersThe Issues Tracker script numbers a new issue one higher than the highest existing number. The email-notification script numbers it by counting rows, so if a row has ever been deleted it can repeat a number already in use. Check new numbers occasionally, and avoid deleting rows — set a status instead.
How the script finds an issueWhen a note or status is saved, the Issues Tracker script finds the row by its category and topic together, not by its ISS number. Keep every issue’s topic distinct within its category; two issues with the same category and topic would be confused, and only the first would be updated.

2. How an issue moves through the system

  1. An issue is added (Hub Admin, or the Manor Advisor’s page) and given a number and category.
  2. The Community Manager records progress and changes the status in CM Update.
  3. The RC (or SC or Manor Advisor) adds responses in RC Issues. Each response is tagged and dated and is added to the Notes cell, so the history builds up; the pages split it into separate, labelled entries for easy reading. Untagged text in older rows is the CM’s own early notes.
  4. Residents follow it on the public tracker; it can be printed for meetings.
Categories and the resident viewThe public tracker maps the Sheet’s categories to friendlier group names and ignores stray capitals or double spaces, so a typo does not create a duplicate group. If you add a new category, add it to the mapping in both progress-tracker.html and print-issues.js so the screen and the printout match.

3. RC and SC Action Registers

In one sentenceCommittee action items (“who will do what by when”) are kept in the BDRV RC Action Register Sheet — one tab for the RC and one for the SC — managed by a single script (wG6RXWVp) that is told which board to use.
  • action-register.html — RC actions: add and edit inline, change status, link an action to an issue number (ISS-xx) with type-ahead search. Committee PIN. References run A-001, A-002…
  • sc-action-register.html — the same for the Social Club, in SC green, with references S-001, S-002…
  • Columns (both tabs): A ref, B meeting, C action, D owner, E due, F issue number, G status (Open, In Progress, Done or Deferred), H notes, I added by, J added date, K outcome (filled in when marked Done).
  • members-area.html — after choosing their name, committee members can update the status and notes of actions.
Two lessons learned (2026)
  • Row numbers: the script expects real sheet row numbers (header = row 1, first action = row 2) and refuses row 1. An earlier off-by-one error wrote edits onto the previous action; it was fixed, but edits made before the fix may sit on the wrong row.
  • Feed delay: the page no longer re-reads the published feed straight after a save, because the feed can lag several minutes and was making correct saves appear to revert.

4. Raise a Concern

  • raise-a-concern.html — residents enter the Residents PIN, then submit a concern or suggestion privately. The Resident Submissions script (zaoV8H-1) saves it to the ResidentSubmissions tab of the Resident Concerns Sheet with status “New”. Columns: Timestamp, Name, Unit, Contact, Category, Description, Status, Chair Notes, Date Discussed, Linked Issue Ref. The menu shows it as an amber “members-only” link.
  • chair-submissions.html — intended as the RC Chair’s private page for reading submissions and recording status, notes, date discussed and a linked issue. The script side is ready (it only answers when given the chair key), but the page’s script address was never filled in and no page links to it. Submissions are currently read and annotated in the Sheet itself. Connecting it is a one-line change.
  • hub-raise-a-concern.html — an older, light-styled copy of the form that no page links to. Candidate for removal.
PrivacyConcerns can contain personal matters. The Resident Concerns Sheet must never be published to the web, and should be shared only with those who need to read it.
