1. The three parts

The Hub is a static website: a collection of ordinary web-page files with no server or database of its own. Everything that changes — events, notices, transactions, photos — is kept in Google, and the pages fetch it when someone opens them. There are three parts:

  1. The website files (HTML pages plus a few shared files) are kept in a GitHub repository called rabdctee/residents-hub. GitHub also hosts them for free through a service called GitHub Pages, and the address bdrv.au points there.
  2. Google Sheets and Google Drive hold the information. Sheets act as the Hub’s database (one Sheet per system, more or less). Drive holds uploaded files: minutes, newsletters, photos, videos, bank statements.
  3. Google Apps Scripts are small programs attached to the Sheets. Each is published as a “web app” with its own long web address. When a page needs to save something, or read something that must not be public, it sends a request to one of these scripts, which does the work inside Google and replies.

2. How a page gets and saves information

Almost every interactive page uses one or more of these four patterns. Recognising them makes any page much easier to understand.

Pattern A — Reading a published Sheet (“CSV feed”)

In Google Sheets, File → Share → Publish to web makes one tab available as a read-only CSV file at a long address beginning docs.google.com/spreadsheets/d/e/2PACX-…/pub?gid=…&output=csv. The page downloads that file and builds its display from it. The number after gid= identifies the tab.

Two things to know about published feeds

They lag. Google refreshes a published feed every few minutes, not instantly. A change saved a moment ago may not show for up to about five minutes. Several pages update their own screen straight after a save so the person doesn’t see old data (this was the cause of the Action Register “status reverting” problem in 2026).

They are public. Anyone who has the address can read the whole tab. Only publish tabs whose contents you would be content for anyone to see.

Pattern B — Asking an Apps Script for data (“getEvents”, “gallery”…)

The page calls a script’s address with ?action=something on the end, and the script replies with data in a format called JSON. This is used where data needs tidying first, or should only go out to someone who supplies a key. Examples: ?action=getEvents (events list), ?action=gallery (event photos).

Pattern C — Sending a save to an Apps Script

The page sends (“POSTs”) the information to a script with an action name such as addEvent, recordTransaction or updateStatus. The script writes it into the Sheet or saves a file to Drive.

Many older pages send in “no-cors” mode: the browser sends the information but is not allowed to read the reply. Those pages simply assume the save worked and update the screen straight away. That keeps them simple, but if the script fails, the page cannot tell. If a save “didn’t stick”, check the Sheet itself.

Pattern D — Reading a Sheet through the Google Sheets API

A small events widget in the Home page’s side column reads the Web Content Manager Sheet directly using Google’s Sheets API and an API key written in the page. This is unusual on the Hub — most pages use Pattern A or B.

3. Shared building blocks

It is a single-page app: one file containing ten sections (Home, About, Newsletters, Calendar, Events, Activities & Contacts, Noticeboard, Village Info, Useful Links, Contacts). JavaScript shows one section at a time, chosen by the menu or by the address (e.g. index.html#events). It is the largest file on the site (about 4,000 lines).

quotes.txtThe list of quotes the Home page picks from.
CNAMEOne line, bdrv.au. Tells GitHub Pages which address the site answers to. Do not delete or edit.
images/, videos/Pictures used by pages, and the Hub-hosted event videos (see Chapter 4).

The look: colours and styling

Since September 2026 the Hub uses a navy, gold and cream palette, chosen for readability. Each page defines the colours at the top of its own styles:

NameColourUsed for

--hub-gold#D4B860Headings, buttons, links
--hub-cream#F6F2E7Body text

Some colours carry a meaning and were deliberately kept when the palette changed: red for urgent or danger, green for success, amber for official or restricted (e.g. the “members-only” menu links), RC blue, Social Club green, Manor purple and Body Corporate burgundy on the committee pages, plus page-specific colour sets such as the six Classifieds categories and the four issue statuses. Several older admin pages still use the earlier light design with a “dark mode” block added at the end of their styles.

Each page carries its own copy of its styles (there is no single site-wide stylesheet in use; an old styles.css file remains but nothing loads it). This makes pages independent, but means a site-wide style change has to be made page by page.

4. PIN locks and what they really protect

About 30 pages ask for a PIN. There are several different PINs: a Residents PIN (Residents Only, Raise a Concern, Fireside Talks), committee PINs, the Hub Admin PIN, and individual PINs for pages such as CM Update, Manor Issues, Village Calendar, Body Corporate and Text Updates. After a correct PIN the page remembers it until the browser tab is closed (using the browser’s “session storage”).

Important: most PINs are only a curtain, not a lock

On most pages the correct PIN is written in the page’s own code, and the repository is public. Anyone who views the page source, or browses the repository on GitHub, can read it. Likewise, the published Sheets that sit behind locked pages (for example the Residents Contact List) can be read by anyone who finds their address. The Village Calendar admin page also contains its Apps Script’s “secret key” in the same visible way.

So PINs keep casual visitors out, but would not stop a determined person. The safer model already exists on the Hub: the Asset Register sends the PIN to its Apps Script, and the script checks it and only then hands over the data. See Risks & recommendations.

The PINs themselves are recorded only in the private Hub Secrets Register, never in this handbook.
